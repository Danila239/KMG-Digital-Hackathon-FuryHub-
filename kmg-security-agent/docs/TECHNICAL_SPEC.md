# Техническое задание первой демоверсии KMG Security Agent

Версия: 0.1. Дата: 24 сентября 2026 года.
Статус: принят пользователем; начата реализация консольной версии. Раздел 2 сохраняет состояние на момент согласования. Актуальные результаты разработки — в VALIDATION.md.

## 1. Цель

Создать отдельный инструмент для разработчиков, который читает исходный код, конфигурацию и документацию проекта, проверяет восемь требований информационной безопасности из ТЗ хакатона, формирует доказательный отчет и возвращает результат для CI/CD.

Пользователь инструмента — разработчик или специалист ИБ. Проверяемый продукт — учебная система службы поддержки KMG-Digital-Hackathon. Модель Qwen используется как компонент анализатора. Она не встраивается в пользовательский интерфейс службы поддержки.

Ожидаемый результат первой демки: одна команда запускает реальный анализ проекта через OpenRouter; появляются JSON и Markdown с находками и восемью статусами; автоматическая проверка разрешает либо блокирует следующий шаг конвейера.

## 6. Конфигурация и пользовательский сценарий

Основные настройки:
- OPENROUTER_API_KEY — секретный ключ; только окружение или .env агента.
- OPENROUTER_MODEL — изначально qwen/qwen3.8-27b:free.
- Адрес API — OpenRouter по умолчанию, с возможностью настройки другого сервера.
- Таймаут, лимит запросов, параллелизм и каталог отчетов — параметры агента.

Подключение к модели выделяется в отдельный модуль. Для перехода на сервер организатора потребуется изменить конфигурацию или адаптер API; модуль анализа проекта и формат отчета сохраняются. Совместимость неизвестного сервера заранее не гарантируется.

Планируемые команды, которые появятся после реализации:

~~~
kmg-agent doctor
kmg-agent scan --repo ../KMG-Digital-Hackathon --output reports/demo
~~~

doctor проверяет конфигурацию и делает небольшой реальный запрос к модели без передачи репозитория. Выводит факт успеха, модель и время ответа, но не ключ и не заголовки авторизации.

scan:
1. Проверяет входные пути и лимиты.
2. Фиксирует версию и состав анализируемого проекта.
3. Читает исходники и требования.
4. Строит индекс и пакеты контекста.
5. Выполняет анализ и проверку доказательств.
6. Формирует результаты и код завершения.

Программа не запускает manage.py и не импортирует модули проверяемого проекта ради анализа. Содержимое файлов рассматривается как данные; инструкции, найденные в коде или документах проекта, не получают права управлять агентом.

Отчеты, временные файлы и кеши создаются вне каталога проверяемого проекта. Каталог output внутри target отклоняется.

## 7. Полнота анализа и работа с контекстом

### 7.1. Инвентаризация

Для каждого обнаруженного файла фиксируются:
- Относительный путь, тип, размер и хеш анализируемого содержимого. У исключенных секретных/рабочих файлов content hash отсутствует: ради хеширования их содержимое не читается.
- Решение: анализировать, обработать как ресурс либо исключить.
- Причина исключения.
- Статус обработки и связанные задания анализа.

Исключаются рабочие секреты и данные: .env, закрытые ключи, runtime, базы данных, журналы, виртуальные окружения, .git и генерируемые артефакты. Имена и причины исключений сохраняются без чтения и вывода секретных значений.

Исходники, конфигурация, зависимости, CI/CD и документация входят в анализ. Папка src/helpdesk не исключается как «чужая библиотека»: из нее реально используются модели и другие компоненты.

Встроенные сторонние статические ресурсы учитываются в инвентаризации, а их активное подключение и значимость для проверяемых требований рассматриваются отдельно. Игнорировать их целиком без объяснения нельзя; обещать полноценный аудит каждого минифицированного пакета в первой версии также нельзя.

Новый исходный файл должен обнаруживаться автоматически. Нельзя опираться только на заранее известные имена portal/views.py и другие места найденных нами дефектов.

### 7.2. Связи между файлами

Индекс строится по AST Python и дополнительному поиску ссылок. Он включает импорты, функции, классы, декораторы, URL-маршруты, настройки, модели и сигналы.

Для предметного анализа собираются цепочки:
- URL → view → проверка доступа → область данных.
- Settings → middleware → backend аутентификации.
- Модель → поле → способ хранения → ключ.
- Операция чтения/записи/bulk → аудит → локальный буфер → collector.
- Входящий HTTP/TLS → proxy → приложение.

Индекс является вспомогательной картой. Он не считается полным доказательством всех возможных динамических вызовов Python.

### 7.3. Анализ пакетами

Сначала выполняется обзор всех релевантных исходников и документов. Затем формируются связанные пакеты по каждому требованию ИБ.

Большие файлы разбиваются на фрагменты с сохранением путей и исходных номеров строк. Превышение контекста не должно приводить к молчаливому обрезанию файла или пропуску оставшихся файлов.

Manifest содержит список фрагментов с диапазонами строк или разделами документа, их хешами и связью с заданиями. Каждый исходный файл должен быть полностью покрыт обзором либо иметь проверяемое основание исключения. Решение модели «файл нерелевантен» само по себе не исключает его из обязательного обзора.

Файл считается обработанным только после успешного анализа всех соответствующих заданий; включения пути в manifest недостаточно. Для выводов используются исходные фрагменты кода, а не только краткие пересказы предыдущих ответов.

При недоступном критически важном фрагменте или незавершенном обязательном задании нельзя выдавать общий успешный результат. Причина отражается явно.

## 8. Проверки по восьми требованиям

| ID | Что требуется проверить |
|---|---|
| ИБ-01 | Все административные маршруты и операции; серверную проверку бизнес-роли; обходы через staff, superuser, группы и альтернативные API |
| ИБ-02 | Аутентификацию защищенных маршрутов; подпись и срок токена; существование и активность пользователя; применимые условия прекращения действия |
| ИБ-03 | Клиентскую точку входа, принудительный TLS, версию протокола и шифры; учитывать, что локальный канал proxy → backend разрешен спецификацией |
| ИБ-04 | Хранение персональных полей и их копий; реальные password hashers; шифрование полей и вложений, ключи и пути записи |
| ИБ-05 | Шифрование локального журнала; доступ к ключам и буферу; возможность подмены/удаления до передачи; проверки целостности при передаче |
| ИБ-06 | Наличие шести предусмотренных названий и ссылок в документации; не требовать фактических сертификатов в рамках этого пункта |
| ИБ-07 | Общий аудит чтения, записи, API, экспорта, bulk и отказов; события СУБД; обходы сигналов ORM и пробелы покрытия |
| ИБ-08 | Все форматы выгрузки персональных данных; роль администратора и обязательное событие аудита для каждой выгрузки |

По каждому пункту выводится отдельный статус:
- no_violations_found — обязательный объем проверки выполнен, подтвержденных нарушений не найдено.
- violated — найдено подтвержденное нарушение.
- inconclusive — данных недостаточно для завершения обязательного вывода.
- error — проверке помешала техническая ошибка.

Отдельно от статуса хранится coverage_complete и перечень завершенных/незавершенных заданий. Например, можно уже обнаружить нарушение, но не закончить проверку всех связанных маршрутов; такой пункт не считается полностью обследованным.

Формулировка «нарушений не найдено» не означает сертификат безопасности. Наличие Windows-специфичного кода не запрещает статический анализ на Mac; выводы, зависящие от фактической среды Windows, должны иметь явное ограничение и не выдавать предположение за испытание.

## 9. Доказательства и защита от ложных срабатываний

LLM предлагает кандидатов находок, но не определяет окончательный код завершения.

Каждый кандидат проходит повторную проверку:
- Существует ли указанный файл и участок.
- Совпадает ли цитата с исходником.
- Действительно ли операция подключена или достижима в рассматриваемой конфигурации.
- Нет ли защиты в общем middleware, helper, storage или иной части цепочки.
- Связана ли проблема с конкретным требованием ИБ либо только с дополнительным пунктом спецификации.
- Не повторяет ли кандидат уже описанный дефект.

Схема ответа модели фиксируется до первого анализа: известные ИБ-ID, допустимые статусы, список evidence и кандидатов, ограничения и признаки завершенности. Неизвестные ID/статусы и неверные типы отклоняются.

Если строка или цитата не подтверждается, выполняется ограниченная попытка уточнения. Кандидат нельзя молча удалить и превратить неудачную проверку в no_violations_found: при неразрешенном обязательном выводе задание помечается inconclusive/error.

Модель получает связанные участки и вопрос о возможных контраргументах. Это повышает качество, но не является формальным доказательством корректности. Детерминированно проверяются схема, существование мест, цитаты и покрытие. Достижимость операции и достаточность общей защиты остаются семантической проверкой; ее способ и ограничения записываются.

Отсутствие защиты обосновывается обследованной цепочкой. Одного поиска слова «audit» или отсутствия декоратора в одной функции недостаточно.

Подтвержденная находка содержит:
- Идентификатор, заголовок и критичность.
- Основной ИБ-ID и формулировку требования.
- Основное место и при необходимости связанные файлы.
- Строки либо имя функции/класса/параметра.
- Проверенные фрагменты кода.
- Условия возникновения и последствия.
- Обоснование и рекомендацию.
- Способ подтверждения и ограничения.

Секреты в цитатах маскируются. Для DOCX указываются документ, раздел и текстовый фрагмент; номера строк Python ему не приписываются.

Критичность: critical, high, medium, low. Любая подтвержденная критичность нарушения ИБ блокирует выпуск; порога «блокировать только high» в исходном ТЗ нет.

## 10. Отчеты, коды завершения и ошибки

### 10.1. Обычный завершенный анализ

Результаты:
- report.json — основной валидированный результат.
- report.md — человекочитаемое представление того же JSON.
- manifest.json — состав и покрытие проекта.
- run.log — безопасный журнал выполнения и итоговая сводка.

Сводка содержит:
- Версию схемы и идентификатор запуска.
- SHA проверяемого проекта и отдельно версию агента.
- Признак локальных изменений и хеш фактически проанализированного содержимого.
- Время начала/окончания с часовым поясом и длительность.
- Модель и доступную информацию о поставщике.
- Число запросов, повторы и расход токенов по данным API; при отсутствии usage явно «неизвестно».
- Общий результат и exit code.
- Все восемь статусов.
- Блокирующие находки, дополнительные наблюдения, ошибки и ограничения.
- Покрытие и исключения.

Отчеты и код завершения вычисляются из одного результата. Markdown не формируется отдельным свободным ответом модели.

### 10.2. Решение для CI/CD

| Условие | Код |
|---|---:|
| Все обязательные проверки завершены; нарушений ИБ нет | 0 |
| Все обязательные проверки завершены; есть нарушение ИБ | 1 |
| Обязательная проверка не завершена: API, разбор, лимит времени/запросов или критически неполные данные | 2 |

Предлагаемая политика при одновременных находках и неполном анализе: код 2 имеет приоритет; уже подтвержденные находки не теряются. Это проектное решение, поскольку приоритет прямо не определен исходным ТЗ.

Дополнительные замечания к спецификации не превращают код 0 в 1. Необоснованные предположения не учитываются как подтвержденные нарушения. Невозможность завершить обязательную проверку остается кодом 2.

### 10.3. Противоречие документов и выбранная трактовка демки

Исходное ТЗ одновременно требует:
- П.4.3.4: артефакт отчета независимо от результата.
- П.4.7.2: частичный отчет при превышении времени.
- П.4.7.3: при ошибках внешнего сервиса — аварийное завершение без отчета.

Для демки предлагается следующее различение:
- При исчерпании общего времени — частичный report.json/report.md, незавершенные статусы и код 2.
- При невосстановимой ошибке внешнего API — код 2, run-status.json, run.log и manifest; окончательный отчет о соответствии не формируется.
- Технический run-status может сохранять уже собранные промежуточные находки с пометкой incomplete, но не выдается за завершенную проверку.

Диагностические артефакты сохраняются всегда, насколько среда позволяет. Непреодолимая остановка процесса или инфраструктуры может помешать записи; после жесткого kill полнота артефактов не гарантируется.

Эта трактовка дает приоритет специальному п.4.7.3. Буквальное требование отчета при любом исходе остается неоднозначным; перед итоговой сдачей желательно подтвердить формат обработки аварий у организатора. Разработка остальных компонентов от этого не зависит.

## 11. Ограничения модели, времени и секретов

- Используется выбранная бесплатная модель; платные модели и случайная смена модели автоматически не подключаются.
- Недоступность выбранной модели дает понятную ошибку. Другая модель выбирается явно.
- Параллелизм и число запросов ограничиваются. Предлагаемое начало — 1–2 одновременных запроса.
- Повторы ограничены общим бюджетом и временем; учитывается Retry-After. Общий дедлайн ограничивает также текущий HTTP-запрос и ожидание между повторами, а не проверяется только между заданиями.
- Предварительная цель — укладывать полный запуск в 25 запросов с учетом повторов. Это инженерная цель до измерений, не обещание достаточности для любого проекта.
- При исчерпании лимита нельзя скрыто пропускать оставшийся код и выдавать успех.
- Предлагаемый внутренний дедлайн анализа — 26 минут, финализация до 27-й минуты; оставшееся время резервируется для остановки и сохранения результатов в пределах 30 минут. Конкретные значения допускается уточнить после измерений без превышения внешнего лимита.
- Расход токенов фиксируется. Стоимость не объявляется нулевой без основания в настройках/API.

Ключ читается только из конфигурации. Не выводятся Authorization, полный .env, тела запросов с секретами и сырой контекст проекта в обычных логах.

В CI ключ хранится в GitHub Secrets. .env не копируется в workflow, артефакты или репозиторий. Перед внешней отправкой исключаются рабочие секреты и маскируются обнаруженные секретные значения в коде. Полная автоматическая гарантия распознавания любых секретов не заявляется.

Подготовка и чтение тестового проекта остаются без записи в него. Ссылки за пределы target и неподдерживаемые объекты файловой системы обрабатываются безопасно и явно. Если содержимое обязательных исходников изменилось другим процессом во время анализа, запуск признается незавершенным; отчет не приписывается неизменной версии проекта.

## 12. План реализации и результаты этапов

| Этап | Работа | Критерий завершения |
|---|---|---|
| 0. Принятие ТЗ | Согласовать объем демки и спорные решения | Пользователь принял документ либо указал изменения |
| 1. Основа и подключение | Пакет Python, конфигурация, .env.example, doctor, HTTP-адаптер | Реальный небольшой запрос к Qwen успешен; ключ не появляется в выводе |
| 2. Чтение проекта | Inventory, DOCX/текст, хеши, исключения, индекс AST | Получен manifest; исходный проект не изменен; файлы и связи обнаруживаются автоматически |
| 3. Один вертикальный сценарий | Реализовать ИБ-01 от входа до JSON/MD и exit code | Реальная модель обнаруживает проблему с правами и дает проверяемое доказательство |
| 4. Полные восемь требований | Проверочные инструкции, связанные пакеты и общий анализ | Все восемь пунктов присутствуют; нет молчаливых пропусков |
| 5. Надежность и точность | Проверка доказательств, дедупликация, ошибки, таймауты, тесты | Пройдены автоматические тесты и контроль ложных срабатываний |
| 6. Локальная демка | Полный живой запуск на предоставленном target | Отчеты, сводка, расход ресурсов и код результата согласованы |
| 7. GitHub Actions | Репозиторий решения, секрет, workflow, артефакты и зависимый demo-шаг | Push запускает проверку; ненулевой результат блокирует зависимый шаг |
| 8. Подготовка сдачи | README, описание архитектуры, материалы и ограничения | Другой человек может воспроизвести проверку по инструкции |

Этап 3 — промежуточная техническая проверка архитектуры, а не завершенная демоверсия. Первой полноценной локальной демкой считаются этапы 1–6; демонстрацией связи с CI/CD — завершение этапа 7.

Оценка часов не фиксируется до первого запроса к модели и измерения скорости. Возможные задержки бесплатного API не должны скрываться за обещанием точного срока.

## 13. CI/CD и границы демонстрации

Workflow хранится в репозитории агента, чтобы не изменять предоставленный тестовый проект. Он получает исходники цели в отдельный каталог и фиксирует именно target SHA.

Для первого стенда push в репозиторий решения запускает:
1. Подготовку агента и checkout заданной версии цели.
2. Тесты инструмента.
3. Отдельный шаг security scan.
4. Публикацию результатов через always().
5. Зависимый демонстрационный шаг выпуска только при успехе security job.

Demo-шаг подтверждает разрешение выпуска; он не обозначается как реальный production deploy, если сервера развертывания нет.

Автоматическая реакция именно на push в репозиторий проверяемого продукта требует подключения со стороны его владельца: внешнего webhook/dispatch, общей CI-интеграции или согласованного зеркала. Push в репозиторий агента нельзя выдавать за уже настроенный trigger целевого продукта.

Блокировка merge дополнительно требует обязательной проверки в настройках защиты ветки. Создание workflow само по себе не запрещает слияние в чужом репозитории.

Сначала демонстрируется стенд решения. Подключение к репозиторию организатора и его правилам защиты — отдельный интеграционный этап при наличии доступа.

## 14. Испытания и критерии приемки

Для инфраструктуры используются имитации ответов API: они позволяют надежно проверять обработку ошибок и коды завершения без расхода квоты. Они не доказывают качество анализа Qwen. Живые проверки модели отмечаются отдельно.

Обязательные автоматические тесты:
- Правильная загрузка конфигурации и отсутствие ключа в логах/отчетах.
- Разбор исходников, таблиц DOCX и сохранение корректных местоположений.
- Исключение .env, runtime, ключей и рабочих данных.
- Для каждого ИБ-пункта — небольшой пример с нарушением и пример с корректной защитой.
- Минимум два примера требуют связать несколько файлов.
- Защита в middleware/helper не объявляется отсутствующей только из-за ее отсутствия во view.
- Переименование файлов и функций не разрушает обнаружение общей проблемы.
- Новый модуль с маршрутом попадает в анализ без редактирования списка файлов.
- Несуществующая строка/неверная цитата не публикуется как проверенное доказательство.
- JSON, Markdown, счетчики и exit code согласованы.
- Сценарии 0/1/2, недоступность модели, 429, таймаут, поврежденный JSON и незавершенное покрытие.
- Неизменность исходного дерева до и после запуска.

Отдельный живой приемочный набор для Qwen включает минимум одну безопасную и одну небезопасную ситуацию по каждому из восьми требований. Это проверка качества модели на размеченных нами примерах; она запускается перед приемкой/сдачей и после существенных изменений промптов, а не обязательно на каждом push. Расход квоты на этот набор учитывается отдельно от одного полного анализа target.

Приемка локальной демки:
- Одна команда выполняет проверку без вопросов к пользователю.
- Подготовлена явная инвентаризация всего проекта.
- Есть хотя бы один полностью завершенный живой анализ текущего target по всем восьми требованиям. Для основного приемочного запуска незавершенный результат не является успехом демки; корректный код 2 проверяется отдельно как аварийный сценарий.
- Есть отдельный результат для каждого из восьми требований.
- Живой анализ находит контрольные реальные нарушения: административные права, анонимный доступ/токен, JSON-выгрузку без контроля и пробелы аудита.
- Известные корректные механизмы — Argon2, шифрование вложений, проверка основной карточки и защищенный CSV — не объявляются отсутствующими.
- Нет заранее зашитого готового списка уязвимостей проекта.
- Все опубликованные доказательства привязаны к существующему коду.
- Запуск завершен за установленное время; расход запросов и токенов сохранен.
- Повторный запуск позволяет сравнить состав находок; полная идентичность текста LLM не обещается.

Контрольные находки используются только для оценки демки и тестов. Производственный анализатор не получает ручной отчет как готовый ответ.

Официальная эталонная версия и скрытая разметка пока недоступны. Искусственные безопасные fixtures и исправленные тестовые копии не называются официальным эталоном. Исправления для испытаний делаются только в собственных fixtures/копиях вне исходного target.

## 15. Что получаем на выходе

Локально:
- Отдельный репозиторий агента с исходниками и проверочными инструкциями.
- Рабочее подключение к Qwen.
- README и пример конфигурации.
- JSON/Markdown отчеты и manifest.
- Автоматические тесты.
- Зафиксированные ограничения.

Для хакатона дополнительно:
- Репозиторий с workflow и секретом в настройках GitHub.
- Лог шага проверки с кодом, количеством и ID нарушенных требований.
- Commit проверенного проекта.
- Краткое описание архитектуры, методов анализа, полноты и ограничений на 1–2 страницы.
- Время выполнения и расход токенов.
- Демонстрация успешного/неуспешного решения конвейера с честным указанием, где используются fixtures, а где реальные запросы.

Материалы сдачи должны быть готовы не позднее чем за один час до защиты, согласно документу о составе сдаваемых материалов. Конкретная календарная дата защиты пока не задана.

## 16. Решения перед началом реализации

Предлагается принять следующие исходные решения:
1. Первая версия — CLI и отчеты, без веб-интерфейса.
2. Анализ — статический, с LLM и проверкой доказательств; произвольный код цели не исполняется.
3. Первая модель — qwen/qwen3.8-27b:free через OpenRouter.
4. Исходный KMG-Digital-Hackathon не изменяется.
5. Разработка ведется на Mac; специфические испытания Windows откладываются до доступа к подходящему стенду.
6. Реализация начинается с doctor и одного сквозного ИБ-сценария, затем расширяется до всех восьми.
7. Ошибка или незавершенная обязательная проверка не выдается за успешную.
8. Первая CI-демонстрация запускается в репозитории решения; интеграция с событиями чужого репозитория учитывается отдельно.

После согласования этого ТЗ следующий конкретный результат — созданная основа проекта и успешный doctor с реальным ответом выбранной модели. До согласования реализация не начинается.

## Изменение организации репозитория для командной работы

По последующему указанию пользователя обе папки публикуются в одном отдельном репозитории `pavlodar`. Активный workflow находится в корневой `.github/workflows/`, цель анализа — соседний каталог из того же commit. Это уточнение заменяет первоначальный план двух независимых репозиториев и checkout внешней цели. Код приложения при объединении не изменяется. Отчеты используют SHA общего репозитория, относительный путь цели и хеш анализируемого содержимого.
