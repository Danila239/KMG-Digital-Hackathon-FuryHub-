# Описание подхода — команда FuryHub

**Хакатон KMG Digital:** «ИИ-агент для автоматизированной проверки функций ИБ в процессе разработки ПО с интеграцией в CI/CD».
**Репозиторий (форк репозитория организатора):** https://github.com/Danila239/KMG-Digital-Hackathon-FuryHub- · **Проверенный коммит тестового проекта:** `576e58100d7ef832cef2ad3ec73fc89ab98f84b5`

## 1. Архитектура решения

Решение размещено в форке репозитория организатора: проверяемый проект — корень форка (файлы организатора не изменяются, п. 5.7 ТЗ), агент — папка `kmg-security-agent/` (исключается из проверки автоматически), шаг CI — `.github/workflows/security-check.yml`.

Агент — консольное приложение на Python 3.11+ (только стандартная библиотека; Windows, Linux, macOS). Он запускается отдельным шагом GitHub Actions на каждый push, проверяет проект целиком и возвращает код завершения: `0` — нарушений нет, `1` — нарушения найдены (слияние и развёртывание блокируются), `2` — проверка не выполнена.

| Модуль (ТЗ 4.2) | Реализация |
|---|---|
| Интеграция с CI/CD | `.github/workflows/security-check.yml`: тесты агента (Ubuntu + Windows) → шаг «ИБ-проверка» → `Deploy gate` только при коде 0; отчёт — артефакт сборки при любом исходе; сводка в журнале шага |
| Сбор контекста | `inventory.py`, `readers.py`: полный обход проекта без перехода по ссылкам, исключение секретов до чтения, чтение кода, конфигурации и DOCX; `manifest.json` с судьбой каждого файла |
| Анализ | слой 1 — детерминированные правила (`static_rules.py`); слой 2 — LLM (`analysis.py`, промпты `resources/system.md`, `resources/skills/ib-01…08.md`) |
| Формирование отчёта | `reporting.py`, `html_report.py`: `report.json`, `report.md`, `report.html`, `run.log` |
| Принятие решения | `decision.py`: код завершения вычисляется детерминированно, модель не может «разрешить» выпуск |

**Модель (LLM):** только Qwen или DeepSeek (требование организатора). Подключается через OpenAI-совместимый API (`/chat/completions`) переменными `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`: Qwen через OpenRouter (`qwen/qwen3.8-27b:free` по умолчанию), DeepSeek (`deepseek-chat`) или модель, развёрнутая организатором. ## 2. Методы анализа

**Слой 1 — детерминированные правила** (разбор AST и конфигурации, код цели не импортируется и не исполняется):

- карта маршрутов от `ROOT_URLCONF` через `include()`; для каждого маршрута вычисляются реальные серверные проверки: `login_required` в URLconf и декораторах, собственные декораторы и helpers, отказывающие в доступе, глобальный middleware, проверка заголовка `Authorization`; разрешаются абсолютные и относительные импорты;
- ИБ-01: у административных маршрутов проверяется роль администратора, а не `is_staff` / `is_superuser` / группы;
- ИБ-02: аутентификация на каждом защищённом маршруте; срок действия токена (`max_age` ≤ 15 мин); срок сессии ≤ 60 мин; `HttpOnly`;
- ИБ-03: шифронаборы (только ECDHE + AEAD), минимальная версия TLS, перенаправление HTTP→HTTPS, `Secure`-cookie, HSTS, отключение проверки сертификатов;
- ИБ-04: хешер паролей (argon2/bcrypt/scrypt), присваивание пароля без хеширования, поля ПД модели пользователя — «шифрованное» поле засчитывается, только если реально вызывает шифрование;
- ИБ-05: размещение ключа журнала, права на каталоги журнала, запись событий без шифрования;
- ИБ-06: шесть обязательных ссылок п. 3.1 ТЗ в README;
- ИБ-07: аудит всех обработчиков (или общим middleware), массовые `QuerySet.update()` в обход сигналов, журнал событий СУБД;
- ИБ-08: каждая выгрузка (включая API, отдающий справочник пользователей) — роль администратора и явная запись аудита.

Находки с общей причиной объединяются (один декоратор на четырёх маршрутах — одна находка). Несоответствия технической спецификации, не относящиеся к ИБ-01…08, выводятся отдельным разделом и пайплайн не блокируют (ТЗ 4.8.1).

**Слой 2 — LLM:** пакетный обзор всех фрагментов проекта по восьми требованиям, затем восемь межфайловых проверок, каждая со своим промптом-скиллом, реестром требования и отобранным контекстом. Код проекта — недоверенные данные: инструкции в комментариях игнорируются. Секреты маскируются до отправки в модель.

**Проверка доказательств:** путь, номера строк и цитата каждой находки (правил и модели) сверяются с исходным файлом. Непроверяемые находки не публикуются.

**Гибридный режим (по умолчанию):** находки обоих слоёв объединяются без дублей. Если модель недоступна (нет токенов, HTTP 429, таймаут), итог формируется по правилам с явной пометкой в отчёте; флаг `--strict-llm` превращает такой сбой в код 2.

## 3. Полнота анализа (ТЗ 4.4.4)

- Проверяется **весь** проект, а не изменённые файлы: 199 файлов, 226 фрагментов. Для каждого файла в `manifest.json` указано решение (анализ, ресурс, исключение) и причина.
- Сквозные требования проверяются по связям компонентов: маршрут → декоратор/helper/middleware → настройки.
- При ограничении контекста модели проект делится на пакеты (до 140 000 символов). Каждый фрагмент должен быть подтверждён моделью как просмотренный. Затем под каждое требование отбираются связанные файлы. Если обязательный контекст не помещается, требование помечается незавершённым — ничего не обрезается молча.
- Изменение файлов во время проверки делает результат незавершённым (код 2).

## 6. Известные ограничения

- Анализ статический: код проекта не запускается; права Windows ACL и среда развёртывания проверяются только по коду.
- Правила рассчитаны на типовые реализации Python/Django; нестандартные механизмы защиты распознаёт LLM-слой.
- Проверка цитат подтверждает место в коде, но не правильность семантического вывода модели; метод выявления указан у каждой находки.
- На Windows используется переносимое чтение файлов (ссылки и junction не обходятся), без атомарного `openat`, доступного в Linux/macOS.

## 7. Соответствие требованиям Республики Казахстан

**Предмет проверки.** Требования ИБ-01…ИБ-08, которые проверяет агент, сформулированы организатором на основе нормативной базы п. 3.1 ТЗ: Закон РК № 418-V «О кибербезопасности», Закон РК № 94-V «О персональных данных и их защите», Единые требования в области ИКТ и ИБ (ПП РК № 832), СТ РК ISO/IEC 27001-2023, СТ РК ISO/IEC 27002-2023, СТ РК 1073-2007. Сертификация и испытания в рамках хакатона не требуются (п. 3.3 ТЗ).

**Безопасность самого агента.**

- Код проверяемого проекта не импортируется и не исполняется; репозиторий не изменяется.
- Файлы секретов, ключей, баз данных и журналов (`.env`, `*.key`, `*.pem`, `*.sqlite3`, `runtime/` и др.) исключаются **до чтения**; прочие секреты маскируются до отправки в модель и перед записью отчёта.
- Ключ модели хранится в GitHub Secrets / локальном `.env` (исключён из Git) и не попадает в код, журналы и отчёты.
- Инструкции, встроенные в код проверяемого проекта, рассматриваются как недоверенные данные.
- Каждый запуск сохраняет отчёт, manifest и журнал как артефакт сборки.

**Условия промышленного использования (вне рамок хакатона).**

| Требование | Состояние в решении хакатона | Необходимо для эксплуатации |
|---|---|---|

Допустимость внешней передачи определяет организатор (п. 4.9.2 ТЗ) |
| Защита конфиденциального исходного кода | Секреты исключаются и маскируются | Согласование с подразделением ИБ перечня данных, передаваемых в модель |
| Журналирование и хранение результатов | Артефакты CI (30 дней) | Централизованное хранение по внутренним регламентам |

## Запуск

```powershell
cd kmg-security-agent
$env:PYTHONPATH="src"; $env:PYTHONUTF8="1"
$env:LLM_BASE_URL="<адрес>"; $env:LLM_API_KEY="<ключ>"; $env:LLM_MODEL="<модель>"
python -m kmg_security_agent scan --repo .. --output reports\run
```

Без ключа: `--mode static`. Подробно — `kmg-security-agent/README.md`.
