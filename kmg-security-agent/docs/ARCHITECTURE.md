# Архитектура первой демки

KMG Security Agent — отдельный CLI на Python 3.11+, проверяющий Python/Django-проект по ИБ-01…ИБ-08. Модель вызывается через совместимый HTTP API OpenRouter; исходная конфигурация задает `qwen/qwen3.8-27b:free`. Сам агент использует стандартную библиотеку, включая `ast`, `json`, `urllib`, `zipfile`/XML для DOCX и `unittest`. Зависимости и код целевого приложения не устанавливаются и не исполняются.

## Поток данных и доверие

1. `config.py` читает только конфигурацию агента. Секрет передается HTTP-клиенту, не в аналитический промпт. `doctor` проверяет доступность модели отдельным небольшим запросом без репозитория.
2. `inventory.py` и `readers.py` фиксируют SHA/изменения цели, состав и хеши анализируемых файлов. Секретные и рабочие файлы исключаются до чтения. Текст, Python, конфигурация и DOCX преобразуются в нумерованные фрагменты. DOCX-местоположение относится к извлеченному тексту.
3. `index.py` строит вспомогательные связи импортов, символов, декораторов и маршрутов. `context.py` собирает полный пакетный обзор, затем связанные исходные фрагменты для каждого требования.
4. `analysis.py` получает JSON-кандидатов от модели. Реестр требований, системный промпт и восемь специальных инструкций находятся в package resources и поставляются комиссии в читаемом виде. Код и документация цели остаются недоверенными данными; найденные в них инструкции не исполняются.
5. `schemas.py` проверяет структуру, статусы и ИБ-ID. `evidence.py` сопоставляет пути, диапазоны и точные цитаты, удаляет повторы. Проверка цитаты доказывает расположение кода, но не доказывает правильность семантического вывода модели.
6. `decision.py` детерминированно определяет код; модель не может разрешить выпуск самостоятельно. `reporting.py` сохраняет согласованные JSON/Markdown, manifest и лог вне цели, повторно маскируя секреты.

## Полнота при ограниченном контексте

Триггером может быть один push, но объект проверки — весь текущий состав проекта. Manifest содержит судьбу каждого обнаруженного файла и причину исключения. Каждый анализируемый фрагмент должен быть рассмотрен в пакетном обзоре; обзор не заменяет межфайловую проверку общего механизма. Затем восемь focused reviews сопоставляют операции с middleware/helpers, хранением, настройками и аудитом. Защита в общем компоненте учитывается как контраргумент ложному срабатыванию.

Лимит контекста обрабатывается пакетами и явным списком непоместившихся источников. Нельзя тихо обрезать обязательный код и выдать успех. `coverage_complete` хранится отдельно от статуса требования: найденная ошибка не означает, что анализ остальных путей завершен. Изменение источников во время анализа делает результат незавершенным. Список известных ошибок целевого репозитория в production prompts не передается; имена и маршруты извлекаются из текущего checkout.

## Решение CI и отказоустойчивость

Код `0` означает завершенные обязательные проверки без подтвержденных ИБ-нарушений; `1` — завершенную проверку с нарушениями; `2` — ошибку или неполноту. Приоритет `2 > 1 > 0` сохраняет информацию о сорванном анализе даже при наличии находок. Дополнительные дефекты технической спецификации не являются самостоятельным основанием для кода `1`.

Число запросов, ожидания и повторы ограничены. Внутренний бюджет scan по умолчанию — 1560 секунд, отдельного запроса — 180 секунд, запросов — 25; это измеряемые ограничения, не обещание достаточности для любого проекта. CI оставляет резерв для финализации в пределах 30 минут. Модель не заменяется автоматически на платную. Usage фиксируется, а неизвестная стоимость не объявляется нулевой.

Из-за противоречия п.4.3.4/4.7.2/4.7.3 исходного ТЗ принято исключение: при общем timeout формируется частичный отчет, при фатальной внешней ошибке — диагностический `run-status`, manifest и лог без итогового compliance report. Жесткая остановка runner может помешать сохранению файлов; workflow дополнительно сохраняет технический `ci-status`, насколько инфраструктура позволяет.

GitHub Actions получает агент и цель отдельными checkout, выполняет offline-тесты, сканирует read-only цель с секретом из окружения и загружает artifacts через `always()`. Зависимый `release-check` демонстрирует разрешение следующего шага только при успехе. Это стенд по push репозитория агента, не уже подключенный production deploy и не автоматическая интеграция с чужим репозиторием. Запрет merge требует отдельной настройки required check.

## Оценка качества и ограничения

Детерминированные тесты с подставными ответами проверяют инфраструктуру без расхода квоты. Они не доказывают способность модели находить нарушения. Отдельный live evaluator проверяет 16 размеченных минипроектов — по безопасному и небезопасному примеру на каждое ИБ-требование. Несколько примеров требуют связать защиту между файлами; есть недоверенная инструкция в коде. Разметка используется только для оценки и не отправляется модели. Fixtures не объявляются официальным эталоном.

Первая версия ориентирована на Python/Django. Динамические вызовы Python, настройки вне репозитория и фактическая среда Windows могут требовать ручного подтверждения. Точное место и цитата не исключают ошибку интерпретации. Маскировка не гарантирует обнаружение любого секрета. Полный живой анализ цели, измерения времени/токенов и опубликованный CI run должны подтверждаться соответствующими артефактами, а не наличием кода или этим описанием.

## Детерминированный слой и гибридный режим

`static_rules.py` строит индекс модулей (без импорта цели), разрешает абсолютные и относительные импорты и собирает маршруты, достижимые от `ROOT_URLCONF` через `include()`. Для каждого маршрута вычисляются фактически применяемые серверные проверки: `login_required` в URLconf и декораторах, собственные декораторы и helpers, отказывающие в доступе (`PermissionDenied`, 401/403), глобальный middleware, чтение заголовка `Authorization`. Правило ИБ-01 требует сравнения `role` с администратором, а не `is_staff`. ИБ-02 требует аутентификации на каждом защищённом маршруте и `max_age` при проверке подписанного токена. ИБ-08 требует роли администратора и события аудита у каждой выгрузки. ИБ-03 проверяет JSON-конфигурацию транспорта (шифронаборы ECDHE+AEAD, минимальная версия, перенаправление HTTP) и параметры cookie/HSTS. ИБ-04 проверяет хешер паролей и поля ПД модели `AUTH_USER_MODEL`. ИБ-05 проверяет размещение ключа журнала и права каталогов. ИБ-06 проверяет шесть ссылок в README. ИБ-07 проверяет аудит обработчиков, массовые `QuerySet.update()` в обход сигналов и журнал событий СУБД.

Находки с общей причиной (например, один декоратор на нескольких маршрутах) объединяются в одну находку с несколькими доказательствами. Несоответствия технической спецификации, не относящиеся к ИБ-01…08, попадают в раздел `additional_findings` и не влияют на код завершения.

В режиме `hybrid` для каждого требования объединяются находки правил и завершённого LLM-анализа. Находки LLM, указывающие на уже отмеченные правилами строки, не дублируются. Если LLM-анализ требования не завершён, статус определяют правила, а в `limitations` указывается причина. Ошибки чтения проекта и изменение исходников во время анализа по-прежнему дают код `2`.

Контроль ложных срабатываний: `tests/test_static_rules.py` проверяет, что на синтетическом Django-проекте с нарушениями срабатывают правила всех восьми требований, а на исправленном варианте находок нет.
