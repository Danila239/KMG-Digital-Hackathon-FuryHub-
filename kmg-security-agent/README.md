# KMG Security Agent — команда FuryHub

Решение хакатона KMG Digital в форке репозитория организатора. Проверяемый проект — корень форка (не изменяется); агент, промпты, тесты и демо-материалы — в этой папке `kmg-security-agent/`, workflow — в `.github/workflows/security-check.yml`. Папка агента автоматически исключается из проверки (в отчёте: `excluded_paths`). Модель — **только Qwen или DeepSeek** (требование организатора).

Консольный анализатор Python/Django-проектов по восьми требованиям ИБ хакатона KMG Digital. Работает в Windows, Linux и macOS, использует только стандартную библиотеку Python.

Анализ состоит из двух независимых слоёв:

1. **Детерминированные правила** ([static_rules.py](src/kmg_security_agent/static_rules.py)) на `ast` и разборе конфигурации. Они строят карту маршрутов от `ROOT_URLCONF`, определяют фактические серверные проверки доступа (декораторы, общие helpers, middleware, проверки токена) и проверяют конфигурацию TLS/cookie, хранение паролей и ПД, ключи журнала, аудит, выгрузки и документацию. Модель для этого не нужна, результат воспроизводим.
2. **LLM-анализ** через OpenAI-совместимый API: пакетный обзор всех фрагментов и восемь межфайловых проверок по [инструкциям](src/kmg_security_agent/resources/skills). Он находит то, что правилами не описано.

Находки обоих слоёв проходят одну и ту же проверку: путь, номера строк и цитата сверяются с исходником. Если модель недоступна (нет ключа, HTTP 429, превышен лимит), итог формируется по правилам с явной пометкой в отчёте, а не завершается кодом 2.

Агент не импортирует и не исполняет код цели, не запускает её сервер и не изменяет исходники. Проверенное состояние — [VALIDATION.md](docs/VALIDATION.md).

## Быстрый запуск

Нужен Python **3.11 или новее**. Все команды выполняются из папки `kmg-security-agent`.

**Windows (PowerShell):**

```powershell
cd kmg-security-agent
$env:PYTHONPATH = "src"
$env:PYTHONUTF8 = "1"
python -m unittest discover -s tests
python -m kmg_security_agent scan --mode static --repo .. --output reports\demo
```

**Linux / macOS:**

```bash
cd kmg-security-agent
export PYTHONPATH=src PYTHONUTF8=1
python3 -m unittest discover -s tests
python3 -m kmg_security_agent scan --mode static --repo .. --output reports/demo
```

Команды запускаются из папки `kmg-security-agent`, `--repo ..` — корень форка. Ожидаемый результат для текущей версии тестового проекта: код завершения `1`, нарушены ИБ-01, 02, 03, 04, 05, 07, 08; ИБ-06 выполнено. В журнал (stderr) выводится сводка с числом нарушений и перечнем требований, в `reports/demo/<время>/` — `report.json`, `report.md`, `manifest.json`, `run.log`.

### Режимы анализа

| `--mode` | Что делает | Нужен ключ модели |
|---|---|---|
| `hybrid` (по умолчанию) | Правила + LLM, находки объединяются без дублей. При сбое модели — вывод по правилам | Желателен |
| `static` | Только детерминированные правила, ~1 секунда | Нет |
| `llm` | Только модель (исходное поведение) | Да |

Флаг `--strict-llm` в режиме `hybrid` возвращает прежнюю строгую трактовку п. 4.7.3 ТЗ: сбой модели — код `2`.

### Демонстрация

- Исправленная командой версия проекта: `demo/KMG-Digital-Hackathon-fixed` (перечень исправлений — `FIXES.md` внутри). `scan --repo demo/KMG-Digital-Hackathon-fixed` → код 0.
- Живой коммит: `python kmg-security-agent/tools/demo_violation.py break|restore` (из корня форка) вносит и убирает одно нарушение ИБ-08 в исправленной версии.
- В CI: ветки `demo/fixed*` проверяют исправленную версию; ручной запуск — параметр `target = fixed-demo`.
- Стресс-тест: `python tools/mutation_test.py`.

### Подключение модели

Модель подключается через OpenAI-совместимый endpoint `/chat/completions`, поэтому подходят Qwen и DeepSeek у любого провайдера: развёрнутые организатором, OpenRouter, официальный API DeepSeek, vLLM, Ollama. По требованию организатора используются только модели Qwen или DeepSeek. Настройки задаются переменными окружения или в `.env` агента (исключён из Git):

```
LLM_BASE_URL=https://<адрес API организатора>/v1
LLM_API_KEY=<ключ>
LLM_MODEL=<идентификатор модели>
```

Старые имена `OPENROUTER_API_KEY` / `OPENROUTER_MODEL` / `OPENROUTER_BASE_URL` поддерживаются. Проверка связи: `python -m kmg_security_agent doctor`.

```bash
python -m kmg_security_agent scan --repo .. --output reports/demo \
  --timeout 1560 --request-timeout 180 --max-requests 25
```

Если файл настроек лежит отдельно, `--env-file` указывается **перед** командой: `python -m kmg_security_agent --env-file path/to/.env scan ...`. Переменные окружения имеют приоритет над `.env`. `.env` проверяемого проекта агент не читает.

### Особенности Windows

В Linux и macOS файлы читаются через `openat`/`O_NOFOLLOW`, это полностью исключает гонки при обходе ссылок. В Windows такого API нет, поэтому используется переносимый режим: символические ссылки, junction и reparse points не обходятся, каждое чтение окружено сверкой метаданных. Режим указывается в отчёте (`target.filesystem_mode`). Общий таймаут через SIGALRM в Windows недоступен: ограничение времени обеспечивают таймауты HTTP-запросов и проверка бюджета между запросами.

Перед внешней отправкой исходников должны быть согласованы выбранный сервис и режим обработки данных. Наличие API-ключа само по себе не означает такого согласования.

## Результат и коды завершения

`--output` — родительская папка. Каждый запуск создает в ней новый каталог с временем UTC и случайным суффиксом. Итоговая строка CLI показывает точный путь. Вывод внутри проверяемого дерева отклоняется.

В каталоге завершенного анализа находятся:

- `report.json` — машиночитаемый результат и восемь статусов требований;
- `report.md` — тот же результат для специалиста;
- `report.html` — наглядный отчёт для браузера (без внешних ресурсов, фильтр по требованиям, светлая и тёмная тема);
- `manifest.json` — состав проекта, причины исключений и покрытие;
- `run.log` — краткий результат и диагностические сведения.

Отчет привязан к фактическому SHA цели, если она является Git-репозиторием, и к хешу анализируемого содержимого. Незакоммиченные изменения отражаются отдельно. В finding указываются ИБ-ID, критичность, объяснение, исправление и проверенная цитата существующего участка. Для DOCX номера относятся к извлеченному тексту, а не к странице Word.

| Код | Значение для `scan` | CI |
|---|---|---|
| 0 | Обязательные проверки завершены; подтвержденных нарушений ИБ нет | Разрешить следующий шаг |
| 1 | Проверки завершены; найдено хотя бы одно нарушение ИБ-01…08 | Блокировать |
| 2 | Ошибка или незавершенное обязательное покрытие, даже если нарушения уже найдены | Блокировать |

Ошибка имеет приоритет над находками: `2 > 1 > 0`. Предупреждения и дополнительные дефекты спецификации сами по себе не дают код `1`. Число находок не является процентом полноты. Точная схема и неизменность цитаты проверяются программно; правильность семантического вывода остается ограничением LLM.

ТЗ организатора одновременно требует отчет независимо от результата, частичный отчет при timeout и завершение **без отчета** при ошибке внешнего сервиса. В демке принято специальное исключение:

- Общий timeout или внутренняя незавершенность: частичный `report.json/md`, код `2`.
- Фатальная ошибка внешнего API: `run-status.json/md`, manifest и лог, **без итогового отчета соответствия**. Уже собранные результаты помечаются незавершенными.
- Жесткое завершение runner/process может помешать сохранению файлов. Ошибка начальной конфигурации до создания каталога выводится в stderr с кодом `2`.

Эта трактовка подробно описана в [ТЗ демки](docs/TECHNICAL_SPEC.md). Документ ТЗ фиксирует исходный этап проектирования; выбранная реализация заменяет предложенные внешние библиотеки эквивалентами стандартной библиотеки и использует `unittest`.

## Проверочные инструкции и полнота

[Реестр требований](src/kmg_security_agent/resources/requirements.json), [системный промпт](src/kmg_security_agent/resources/system.md) и [восемь инструкций](src/kmg_security_agent/resources/skills) входят в исходники. Это skills анализатора по требованиям хакатона.

Агент собирает весь проект, а не только Git diff. Источники разбиваются на фрагменты, проходят пакетный обзор, затем сопоставляются по каждому требованию с учетом импортов, маршрутов, общей защиты и настроек. Все фрагменты должны получить подтверждение рассмотрения. Недостающий контекст и превышенный бюджет учитываются явно. Полноценная модель всех динамических вызовов Python не заявляется.

Рабочие секреты, `.env`, приватные ключи, базы, runtime, `.git`, виртуальные окружения и генерируемые артефакты исключаются без чтения содержимого. Ссылки наружу и неподдерживаемые объекты не обходятся молча. Значимые файлы проверяются на изменения за время анализа. Маскировка секретов применяется до внешней передачи и перед сохранением результатов; универсальное распознавание любых секретов не гарантируется.

Комментарии и документы цели не могут управлять агентом: найденные в них инструкции рассматриваются как недоверенные данные. Модель не получает инструмента исполнения команд.

## Тесты и отдельная оценка модели

Обычные тесты выполняются локально и в CI без сетевых запросов и API-ключа:

```bash
PYTHONPATH=src python3.14 -m unittest discover -s tests -v
```

[Размеченные fixtures](tests/fixtures/README.md) содержат **16** независимых минипроектов — безопасный и небезопасный пример для каждого ИБ-ID. В нескольких случаях защита расположена в другом файле. В одном исходнике есть попытка подменить инструкцию анализатора. Каждый пример оценивается **только по своему требованию**; безопасный пример не является полностью безопасной системой или официальным эталоном организатора. Разметка не отправляется модели.

Живая оценка запускается отдельно:

```bash
PYTHONPATH=src python3.14 -m kmg_security_agent evaluate \
  --fixtures tests/fixtures --output reports/evaluation \
  --timeout 1560 --request-timeout 180 --max-requests 40
```

Это **не менее 16 модельных запросов**, возможны дополнительные попытки и несколько минут ожидания. Оценка расходует отдельную квоту; она не запускается на каждом push. Результаты — `evaluation.json/md`, совпадения по примерам, precision/recall классификации минипроектов и использование API. Это метрики статусов примеров; корректность путей доказательств дополнительно влияет на число совпадений, а точность отдельных находок ими не измеряется. Для `evaluate` код `0` означает совпадение всех ожиданий, `1` — завершенную оценку с расхождениями, `2` — незавершенность. Эта оценка не заменяет проверку на скрытой разметке организатора.

## GitHub Actions

[Workflow](../.github/workflows/security-check.yml) на каждый push:

1. **tests** — юнит-тесты и контрольный прогон правил на Ubuntu **и Windows**.
2. **security-check** — отдельный шаг проверки ИБ всего проекта (`hybrid`). В журнал шага выводятся код завершения, число нарушений и нарушенные ИБ-ID, в сводку прогона — таблица статусов. Отчёты загружаются артефактом при любом исходе.
3. **release-check** — разрешается только при коде `0`. При `1` и `2` шаг блокируется.

Ключ модели задаётся в **Settings → Secrets and variables → Actions**: secret `LLM_API_KEY`, variables `LLM_BASE_URL` и `LLM_MODEL`. Без секрета проверка всё равно выполняется правилами. Ручной запуск (**Run workflow**) позволяет проверить другой репозиторий и ветку, например эталонную версию организатора: параметры `target_repository`, `target_ref`, `target_path`. Чтобы блокировать merge, отметьте `ИБ-проверка (шаг CI/CD)` как required check в правилах защиты ветки.
